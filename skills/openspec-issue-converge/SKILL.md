# OpenSpec Issue Convergence

Analyze the cumulative issue log of an OpenSpec change and produce a convergence verdict: are later issues late-discovered original gaps, *caused by fixing earlier issues*, or generated by one underlying structural flaw? The verdict is the deliverable — a report to the user. `issue.md` is written only on explicit request (Guardrails).

## Input

- Change name (optional). If omitted, infer from conversation context, or auto-select if only one active change exists, or run `openspec list --json` and ask.
- Optionally: which round counts as the "latest" (default: HEAD of the change's `issue.md`).

## Steps

1. **Select the change and load context**

   Announce: `Assessing convergence for change: <name>`.

   ```bash
   openspec status --change "<name>" --json
   openspec instructions apply --change "<name>" --json
   ```

   Read all returned `contextFiles` (proposal, design, specs, tasks, issue) so the analysis is grounded in the change's intent, not the issue text alone.

2. **Inventory the issues**

   Read `openspec/changes/<name>/issue.md` fully (it is a cumulative logbook — a single file may exceed 100KB). For each `ISSUE-<n>` record: title, severity, category, status (`[ ]`/`[x]`), which review run filed it, and which runs' Enrichment/Re-evaluation/Verification notes touched it. Done when every `ISSUE-<n>` in the file has its status, severity, and filing run recorded.

   If the file does not exist or contains no issues, report `NOT_APPLICABLE`.

3. **Reconstruct the loop history**

   For each commit that touched `issue.md`, extract the issue set present, in commit order:

   ```bash
   for c in $(git log --format=%h -- openspec/changes/<name>/issue.md | tac); do
     echo "=== $c $(git log -1 --format='%s' $c)"
     git show $c:openspec/changes/<name>/issue.md 2>/dev/null \
       | rg -o 'ISSUE-[0-9]+' | sort -u | tr '\n' ' '
     echo
   done
   ```

   From this, compute **new issues per review run**: the set of issue IDs first appearing in each code-review commit. When the repo does not use the per-run commit convention, fall back to the `Enrichment <n> (audit, run N)` / `Verification (code-review run N)` note numbering inside `issue.md`. Done when every run has its new-issue count, or a stated no-per-run-history fallback.

4. **Classify each issue**

   | Class | Detection |
   |---|---|
   | **Original gap** | No reference to a prior issue's fix; the condition exists in the change's own implementation. |
   | **Fix-induced** | The issue text (Why it matters / Enrichment) states the trigger was created by fixing an earlier issue. Keywords: "The ISSUE-`n` fix", "residual of the ISSUE-`n` fix", "pre-fix regression", "the ISSUE-`n` fix commit … introduced", "new finding — see ISSUE-`n`". |
   | **Consolidation/hardening** | The audit's verdict is Filter 4 non-functional improvement, or the realistic trigger is narrowed to "a future regression / future unguarded addition". |
   | **Test gap** | Missing test coverage for a substantive contract. |

   Record the parent issue (the one whose fix caused it) for every fix-induced issue — this is the regression chain.

5. **Aggregate the trends**

   - New-issue count per run and its trajectory: zero → converged; declining → near convergence; flat (~2–3/run) → plateau; rising → diverging.
   - Fix-induced share: overall, and separately in the last 3 runs (a rising share is the strongest divergence signal).
   - Severity mix in recent runs vs early runs.
   - Audit-filter outcome trend: rising share of Filter 4 / "future regression only" verdicts means the loop is in hardening mode, and each remaining round will keep returning small consistency items.
   - Backlog: count of unresolved `[ ]` issues. `0` with a recent review that found nothing new → converged.
   - **Gap check:** if the last commit is a fix (`clean`), confirm whether any independent code-review run reviewed the tree *after* it. "Clean" from the fixer's own gate is not a convergence verdict — only a later review finding zero new issues is.

   Done when each bullet ends in a number or an explicit no-data statement.

6. **Map fix-induced issues to architectural root causes**

   Group the regression chains and check whether they share a structural theme. The common archetypes (derive them from the actual issues, never assume):

   - **Duplicated parallel chains** — the same contract (load → validate → decrypt → mode-gate → hash) reimplemented per entry point (startup, reload, admin API, import CLI) with different strictness and different sources of truth. Any fix to one chain desynchronizes it from the others, so the next review finds the new divergence.
   - **Bootstrap/lifecycle ordering coupling** — mutually-constrained startup sequencing (config load vs `setup_otel` vs `setup_logging` vs resource build); fixing one order constraint inverts another.
   - **State-machine bookkeeping breadth** — poll loop + last-seen + locks + drain/watchdog/retry; every fix reveals an adjacent bookkeeping edge.

   Verify the highest-signal theme with one targeted grep in the current tree (e.g. count the `load_secret_blob_map`/`validate_config`/`parse_*` call sites across the entry points, or the number of independent validation functions) — enough evidence to call it structural, not random.

7. **Verdict**

   Assign one verdict and its recommendation from Result Semantics. Pick by the dominant signal: the recent discovery trend first, fix-induced share second, open backlog third. Drop to `NOT_APPLICABLE`/`BLOCKED` when step 2 or 3 established the precondition is absent.

8. **Report**

   ```markdown
   ## Convergence Report: <change-name>

   ### Result
   <VERDICT>

   ### Issue Inventory
   - Total issues: N (open: N, resolved: N)
   - New issues per run: <run: count, ...>
   - Fix-induced: N (regression chains: ISSUE-x → ISSUE-y, ...)
   - Audit-pruned (Filter 4 / hardening): N

   ### Analysis
   <trend, fix-induced share, severity trend, gap check>

   ### Root Cause
   <shared architectural theme, with current-tree evidence>

   ### Recommendation
   proceed to archive / consolidation first / keep fixing / design review
   ```

   Do not restate full issue text — reference issue IDs and cite the evidence lines.

## Result Semantics

- `CONVERGED` — last independent review found zero new issues (or only Filter 4 / cosmetic), backlog empty, fix-induced share small. Recommend `openspec-align`/archive.
- `NEAR_CONVERGENCE` — issues mostly fixed; new ones low-severity, mostly original-late-discovered or consistency. One more review round, or archive as documented-residual.
- `PLATEAUED` — constant discovery rate with a growing fix-induced share → per-issue fixes alone will keep looping; recommend a consolidation refactor targeting the root cause (single shared chain / single load seam) or an explicit archive-with-documented-residual decision.
- `DIVERGING` — fix-induced share and/or severity rising, unresolved backlog growing → stop the loop, escalate to design review; archiving is risky until the root cause is addressed.
- `NOT_APPLICABLE` — no `issue.md` exists or it contains no issues. `BLOCKED` — key context (git history, change artifacts) unavailable.

## Guardrails

- Report-only by default: append to `issue.md` only on explicit request, as a new `**Convergence <run>:**` note after existing content, leaving every existing entry untouched.
- Ground every classification in the issue text and git history — never infer a fix-induced chain without a cited "caused by" statement.
- Do not fix code, do not mark tasks, do not align or archive, do not commit.
- Do not duplicate the work of `openspec-issue-audit` (per-issue triage) — this skill is the *loop-level* verdict, not a per-issue re-audit.
